# Retail DWH

Вимірювальне сховище даних для роздрібної мережі: дві системи-джерела, два факти
зі спільними вимірами, історія змін довідників, шар трансформацій на dbt і звітність у Power BI.

**Стек:** PostgreSQL 16 · dbt 1.12 · Power BI · Docker

---

## Архітектура

```
 ДЖЕРЕЛА                ТРАНСФОРМАЦІЇ              СПОЖИВАЧІ

 src   (роздріб)  ──┐
                    ├──►  dbt  ──►  dbt_star  ──►  Power BI
 wms   (склад)    ──┘                              SQL-аналітика
```

Операційні системи моделюються окремими схемами PostgreSQL. dbt читає їх напряму
й матеріалізує вимірювальну модель у схему `dbt_star`.

### Схеми

| Схема | Призначення | Таблиць | Розмір |
|---|---|---:|---:|
| `src` | система-джерело: роздрібні продажі (OLTP, 3НФ) | 11 | 50 MB |
| `wms` | система-джерело: управління складом | 3 | 26 MB |
| `dbt_star` | вимірювальна модель, що будується dbt | 11 | 90 MB |
| `star` | та сама модель, зібрана вручну (референс для звірки) | 6 | 40 MB |
| `snow` | нормалізований варіант вимірів для порівняння | 11 | 40 MB |

## Вимірювальна модель

Дві таблиці фактів різного типу, об'єднані конформованими вимірами.

```
              dim_date ─────────────────┬──────────────── dim_warehouse
                  │                     │                      │
                  │                     │                      │
   dim_store ── fact_sales ── dim_product ── fact_inventory ── dim_article
                  │                     │
      dim_customer│                     │
                  │                     │
        dim_transaction_type            │
                                        │
                                   stock_cover
```

### `fact_sales` — transaction fact

| | |
|---|---|
| Зерно | одна позиція чека |
| Рядків | 233 015 |
| Період | 2024-01 … 2026-01 |
| Міри | `quantity`, `gross_amount`, `discount_amount`, `net_amount`, `cost_amount` — усі повністю адитивні |

Повернення зберігаються з від'ємною кількістю в тому самому факті, тож чиста виручка —
звичайний `sum(net_amount)`. Скасовані замовлення не завантажуються.
Номер чека зберігається у факті як degenerate dimension — без нього неможливо
порахувати середній чек.

### `fact_inventory` — periodic snapshot

| | |
|---|---|
| Зерно | залишок артикула на складі станом на день |
| Рядків | 254 124 |
| Період | 2025-07-01 … 2025-12-31 |
| Міри | `qty_on_hand`, `qty_reserved`, `qty_in_transit`, `qty_available` — **напівадитивні** |

Міри цього факту складаються за товарами й складами, але **не за датами**: той самий
товар перераховується щодня. Залишок на дату отримують фільтром, середній — через `avg()`.
Опис напівадитивності винесено в `schema.yml`, щоб він потрапив у документацію моделі.

### Виміри

| Вимір | Рядків | Особливості |
|---|---:|---|
| `dim_date` | 1 096 | згенерований, суцільний ряд 2024–2026 без пропусків; ключ у форматі `YYYYMMDD` |
| `dim_product` | 2 001 | конформований: обслуговує обидва факти. Містить спецрядок для складських матеріалів, яких немає в роздрібному асортименті |
| `dim_customer` | 20 401 | спецрядок для продажів без ідентифікації покупця (17,6% чеків) |
| `dim_store` | 30 | місто й область розплющені з довідника джерела |
| `dim_warehouse` | 5 | |
| `dim_article` | 715 | складський довідник; зв'язок із товаром неоднозначний (див. нижче) |
| `dim_transaction_type` | 18 | junk dimension: канал, спосіб оплати, тип транзакції |

## Ключові рішення

**Атомарне зерно.** Обидва факти зберігають найдрібніший рівень, доступний у джерелі.
Агрегати будуються поверх, а не замість.

**Сурогатні ключі як хеш природного ключа** (`md5`). Детерміновані: перебудова моделі
з нуля не змінює ключів, тому факти не «відв'язуються» від вимірів. Побічний ефект —
факт обчислює ключі самостійно й не потребує lookup-join'ів до вимірів, завдяки чому
виміри й факти будуються паралельно.

**Спецрядки замість NULL у зовнішніх ключах.** Продаж без ідентифікованого покупця
та складський артикул без роздрібного товару отримують власні рядки у вимірах.
Inner join нічого не втрачає, а звіт показує осмислений підпис замість порожнього рядка.

**Стан на момент події фіксується у факті.** Джерело не записує собівартість у рядок
замовлення, а `src.products.unit_cost` зберігає лише поточне значення. Тому закупівельна
ціна на дату продажу відновлюється з журналу змін і кладеться у факт сумою `cost_amount`.
Без цього зміна ціни постачальником переписувала б історичну маржу заднім числом:
виміряно на цих даних — 0,72% собівартості, маржа 33,44% проти 32,96%.

Ціна при цьому **не** версіонується у вимірі товарів. Вимір Type 2 описує товар,
а ціна — вхідна величина міри: версіонування породжувало б новий рядок товару
на кожен перегляд цін постачальником.

**Історія змін довідника товарів — SCD Type 2** (реалізовано в схемі `star`).
Один товар має кілька версій із межами дії; факт посилається на версію, що діяла
в день продажу. Гібридний режим: назва й категорія версіонуються, собівартість — ні,
оскільки історичне значення вже зафіксовано у факті.

**Інтеграція другого джерела.** Складська система має власні коди артикулів;
зв'язок із роздробом неповний і неоднозначний — 60 артикулів не мають роздрібного
товару, 15 товарів мають по дві складські картки. Зіставлення виконується в напрямку
«багато до одного» (залишок → артикул → товар), що виключає множення рядків;
вибір підтверджено звіркою кількості рядків із джерелом.

## Контроль якості

**76 тестів dbt** на моделях: унікальність і заповненість ключів, `relationships`
між фактами й вимірами (заміна зовнішніх ключів, яких dbt не створює),
`accepted_values` на категорійних атрибутах. Окремий singular-тест перевіряє,
що періоди дії закупівельних цін не перекриваються — інакше join за діапазоном
дат тихо задублював би рядки факту.

```
dbt build   →   PASS=87   (11 моделей + 76 тестів)
```

**Звірка з джерелом.** Контрольні суми виручки, кількості одиниць і кількості чеків
зводяться з `src` до копійки. Окремо звіряються дві незалежні реалізації моделі —
рукописний ETL (`star`) і dbt (`dbt_star`):

```
                  рядків        net_amount          cost_amount
star             233 015    4 375 145 993,13    2 912 024 151,08
dbt_star         233 015    4 375 145 993,13    2 912 024 151,08
```

## Аналітика

**`stock_cover`** — drill-across двох фактів: залишок на останню дату зрізу проти
темпу продажів за той самий період, у днях запасу на товар.

Факти не з'єднуються напряму — кожен агрегується до спільного зерна (товар),
після чого з'єднуються результати агрегації.

**Power BI** (`star.pbix`) — модель на шести таблицях зі зв'язками, виведеними
із зовнішніх ключів, міри DAX (маржа, маржа %, середній чек) і time intelligence
через `SAMEPERIODLASTYEAR`.

**`04_practice/`** — набір аналітичних запитів: динаміка рік до року, топ-N у категорії,
наростаючі підсумки, ABC-аналіз асортименту.

## Порівняння star / snowflake

Схема `snow` містить ту саму модель із нормалізованими вимірами
(`dim_product → dim_category → dim_category_group`, `dim_store → dim_city → dim_region`).
Обидві схеми завантажені з тих самих даних, і виручка в них збігається. Собівартість у `snow` лишилась
за старою формулою: схема існує лише для порівняння швидкодії, а ці запити читають тільки виручку.

Виміряно на однакових запитах (`02_snowflake/compare.sql`, `EXPLAIN ANALYZE`, прогрітий кеш, медіана 41 прогону):

| Запит | join'ів star | join'ів snow | star | snow | різниця |
|---|---:|---:|---:|---:|---:|
| Виручка за категорією | 1 | 2 | 56 ms | 75 ms | +32% |
| Виручка за областю | 1 | 3 | 51 ms | 85 ms | +67% |
| Топ-20 товарів | 1 | 1 | 61 ms | 63 ms | +3% (у межах шуму) |

95-98% прочитаних сторінок припадає на таблицю фактів; економія місця на нормалізованих
вимірах — близько 1%. Вартість нормалізації — кожен додатковий join, виграш — незначний,
тому базовою обрано зіркову схему.

## Запуск

```bash
docker compose up -d
```

PostgreSQL на `localhost:5433`, Adminer на `localhost:8081`.

Наповнення джерел:

```bash
docker exec -i dwh-postgres psql -U dwh -d dwh -v ON_ERROR_STOP=1 < 00_src/01_schema.sql
docker exec -i dwh-postgres psql -U dwh -d dwh -v ON_ERROR_STOP=1 < 00_src/02_seed.sql
docker exec -i dwh-postgres psql -U dwh -d dwh -v ON_ERROR_STOP=1 < 00_src/03_wms_schema.sql
docker exec -i dwh-postgres psql -U dwh -d dwh -v ON_ERROR_STOP=1 < 00_src/04_wms_seed.sql
```

Генерація детермінована (`setseed`), тому результати відтворюються.

Побудова моделі:

```bash
cd 06_dbt
./dbt.cmd build                      # моделі + тести
./dbt.cmd docs generate --static     # документація з графом залежностей
```

Докладні команди, параметри підключення й особливості Windows — у [RUNBOOK.md](RUNBOOK.md).
